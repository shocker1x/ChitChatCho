# Project Decisions

- The project uses Python's built-in `sqlite3` and JSON seed files to keep setup inspectable and dependency-light. Seed records are explicitly synthetic and use the reserved `.invalid` email domain.
- Gemini is the initial provider for testing, using `GEMINI_API_KEY` and a configurable model (currently defaulting to `gemini-3.8-flash`, following the configured API's availability response). `CompletionClient` is the provider boundary; Anthropic remains available by setting `LLM_PROVIDER=anthropic` and supplying `ANTHROPIC_API_KEY`, for the planned switch after the final phase. No API key is stored in the repository.
- Phase 2 keeps 15 customers and 30 catalog products explicit in JSON, and deterministically generates 40 orders from five status counts (8 per status) plus synthetic shipment rows. This avoids a large repetitive order fixture while keeping volume and state distribution easy to inspect and change.
- Mock tools use the same local SQLite database. Every invocation, including failures and idempotent replays, records its inputs and result. Risky actions require explicit confirmation and a caller-stable idempotency key; identity-bound order tools require order number plus matching email or postcode.
- The API exposes only a health check and a minimal model-backed chat endpoint. Decision orchestration, real integrations, and authentication remain out of scope at this point.
- Phase 1 policy data uses JSON rather than YAML to avoid another parser dependency. Policy lookup accepts explicit situation keys from the policy file instead of attempting natural-language classification; later decision logic is responsible for selecting the situation.
- Phase 3 uses Pydantic records for model output validation and a deterministic gate with precedence: forbidden policy, authority limit, high stakes, identity, missing facts, low-confidence/low-stakes clarification, then explicit confirmation. High-stakes requests are escalated; medium-stakes actions require confirmation. Caller-provided verification/confirmation flags are trusted orchestration state, not inferred from model prose.
- Phase 4 keeps reply generation separate from decision generation. The reply-turn endpoint accepts a validated decision record and tool results, then appends the exchange to a transcript table; it does not load prior turns into the model, leaving conversation memory for Phase 5. The viewer is a small escaped HTML page rather than a full chat UI.
- Phase 5 stores current-chat facts on the conversation and keeps customer preferences plus the most recent completed summary in a separate profile table. Cross-chat profile data is returned only after order number plus matching email or postcode verification. A completed conversation is bound to that verified customer and cannot be rebound using another customer's valid order.
- Verified profile preferences and the previous summary are supplied as explicit known facts for the next conversation. The API derives identity verification from stored mock order/customer data; it does not trust a client-provided `identity_verified` flag.
- Phase 6 stores 60 scripted scenario cases as JSON category defaults plus per-case customer messages and expected-move overrides. The runner persists complete transcripts and judge scores to ignored run output. Hard checks inspect structured actions/results, customer identity markers, supported dates and order statuses, numeric policy claims, and repeated side effects. Calibration uses linearly weighted Cohen's kappa and exact agreement; no human agreement result is reported until 20 transcripts receive human ratings.
